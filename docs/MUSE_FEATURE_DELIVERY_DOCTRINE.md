# Muse 功能交付与使用教学原则

版本：1.0
日期：2026-11-13
性质：长期产品决策 / 本地开发记忆（User Track 的项目偏好由 SQLite 记忆库另行登记）

## 核心要求

Muse 的每一项功能都必须做到「逐一介绍、逐一实现、逐一教学、逐一验收」。不能只展示宏大愿景、静态概念图或没有真实后端支撑的按钮。

对每个功能模块，必须同时交付：

1. **功能介绍**：它解决什么问题、适合什么场景、与其他模块如何协作。
2. **真实状态**：明确标记已实现、部分实现、仅后端、规划中或受依赖阻塞；区分代码存在、接口可用、运行成功和实机验收。
3. **图文教学**：用界面截图/真实界面标注、流程图或结构图配合文字，说明入口、按钮、输入、操作顺序和注意事项。示意图必须标明「示意」，不得冒充实机截图。
4. **操作步骤**：给出用户可以照做的逐步说明，包含必要前置条件、授权、依赖和停止/恢复方式。
5. **预期结果**：说明成功后在哪里看到状态、记录、文件或成品，以及如何确认它确实完成。
6. **边界与风险**：说明当前不能做什么、需要什么本机服务/模型/Provider、数据去向、成本、权限和安全限制。
7. **测试与验收**：为后端、API、前端、持久化、失败恢复和关键用户路径设置可复现测试；真实硬件/外部服务依赖须单独标记实机验收，不得以模拟测试替代。
8. **记忆与进度**：把用户确认的决策写入 User Track；把实现方法、测试、失败和工程经验写入 Agent Track/进度账本；同步用户手册、能力清单和本轮进度报告。

## 逐项推进规则

- 一次聚焦一个完整模块或一个可独立验收的垂直切片，按「盘点 → 设计 → TDD → 后端/持久化 → API → UI → 图文教学 → 回归测试 → 实机验收 → 记录」推进。
- 不以 UI 假数据代替真实 API，不以按钮存在代替功能完成，不以构建成功代替端到端验收。
- 若依赖尚未具备，先把阻塞原因、用户需要做的动作和替代路径讲清楚；继续完成不依赖该条件的工作。
- 每个模块完成后更新功能矩阵和教学内容，再开始下一模块；保留版本、来源、测试证据和未完成项。
- 真实截图优先；无法启动或观察到桌面窗口时，明确说明截图缺失，并提供清晰标记的流程图/示意图，不伪造截图。
- 教学要面向真实使用者，避免要求用户猜按钮、猜路径或在多轮对话中反复寻找入口；尽量把下一步操作放在界面内。

## 标准模块交付模板

- 模块名称 / 版本 / 目标
- 当前状态与证据
- 功能结构图或真实截图
- 使用前准备
- 一步一步操作
- 成功结果与验证方法
- 常见故障与恢复
- 安全、隐私、成本和能力边界
- 自动化测试 / 手动验收结果
- 下一项明确任务

## 当前执行顺序

以 B129 用户手册为基线，继续按能力依赖逐项完成：任务中心与安全操作 → Research Wiki 图谱与反证工作台 → User/Agent 双轨记忆中心 → Routine/提醒/Watchdog 控制台 → Agent/Provider/工具/资源管理 → 设置、托盘、安装更新与桌面实机验收。若代码审计发现依赖顺序应调整，记录理由后调整，不为追求 UI 数量而并行制造空壳模块。
