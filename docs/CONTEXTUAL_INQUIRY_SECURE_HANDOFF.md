## Review-only lease primitives — 2026-11-21

It requires the separate review-only authorization payload and matching reserved audit event, validates the encrypted-envelope shape and pending-state flags, issues a worker lease, and never sets `_approved`. It does not use the generic `claim_next()` scheduler.

## Decision: preserve the existing queue, encrypt before persistence

The smallest viable durable handoff is an encrypted envelope in the existing TaskQueue payload, not a second case database, queue, scheduler, or unencrypted sidecar file.

The Windows-only, standard-library DPAPI adapter is implemented in `src/muse/contextual_inquiry_security.py`. It uses CurrentUser scope and UI-forbidden flags, a fixed application-specific optional entropy value, strict envelope shape/version/size checks, and fails closed on unsupported platforms or native API errors. It must never fall back to plaintext, a hard-coded encryption key, a machine-wide key, or a generated key stored beside the database. DPAPI protects data at rest for this Windows user profile; it is not isolation from malware or other programs already running as the same user.

The CLI asks for a third, independent confirmation before storing the case context. The complete case document—including observations, hypotheses, unknowns, third-party statements and proposed experiments—is persisted only as DPAPI-protected ciphertext in the existing local TaskQueue. Declining preserves the generic placeholder behavior.

The TaskQueue may contain only a versioned envelope with ciphertext and non-sensitive format metadata. It must not contain plaintext case fields, excerpts, source text, stakeholder narratives, or plaintext hashes that expose case content. The pre-approval reader decrypts only after checking task kind, pending-approval state, envelope flags, Ticket identity, canonical JSON, and the workflow contract. It returns the validated object in memory and does not attach or approve it; the dedicated local handler calls it only after review-only authorization and a live lease.

## Approval and execution gates

1. No case-storage consent: keep the current context-reentry placeholder and keep approval blocked.
2. Case-storage consent: persist only DPAPI-protected ciphertext. This alone does not authorize review execution.
3. Unless the dedicated handler is explicitly injected (or enabled through the local-only CLI flag), keep the task non-approvable. A missing or unregistered handler must fail closed, not become a generic fallback.
4. The explicit local handler may produce only provisional candidate findings. The encrypted result returns to `waiting_approval`; a separate human decision is still required before knowledge persistence, claim adjudication, or downstream action.
5. Decryption must be scoped to the current Windows user profile. Moving the database to another Windows account or machine is not a supported recovery path; the user must re-enter the case there.
6. The handler must not automatically execute proposed action experiments or write raw case narratives to long-term memory.

## Evidence-linking requirements

- Resolve every hypothesis `source_refs` and `counter_refs` through the inquiry's observation table.
- Resolve each observation's `source_ref` to exactly one active `source` node in the existing ResearchKnowledgeStore. Missing, ambiguous, inactive, deleted, and non-source references remain unlinked.
- Record resolved references as unadjudicated claim-evidence candidates through the existing store API. It creates `relates` edges only; it does not assert support or refutation.
- Preserve the existing claim lifecycle: newly persisted hypotheses remain `proposed`; any promotion requires verified citation anchors, evidence review, and the store's claim-transition rules.

## Required implementation and validation before enabling execution

- The local contextual-review handler is implemented in `src/muse/contextual_inquiry_local_review.py`. It uses the narrow reader through the dedicated runner, validates a strict candidate-only result schema, and returns DPAPI ciphertext. Do not add a competing scheduler.
- `autonomous_runtime run|once --enable-contextual-review` is the explicit opt-in entry point. It requires a configured local LM Studio/llama.cpp model on an HTTP loopback `/v1` endpoint; the local client bypasses system proxies. Default behavior remains disabled and cloud providers are rejected.
- Verify idempotent task submission cannot silently reuse a different stored envelope or consent state; reject mismatches without mutating the existing task.
- Ensure generic task snapshots, event logs, CLI output, progress telemetry, and errors never reveal plaintext case content.
- If evidence candidates later receive a review, require verified citation anchors, quality/independence assessment, and the existing ResearchKnowledgeStore review lifecycle before any claim transition or supports/refutes edge.
- Run focused tests through the project's psmux-backed `muse_dev.py` command path, then run the broader suite and report unrelated failures separately.

## Execution-path audit — 2026-11-21

A read-only source audit of the current TaskQueue, worker, and AutonomousRuntime establishes additional constraints for the next implementation phase:

- `TaskQueue.claim_next()` claims only `queued` Tickets, creates a worker lease, and returns the full decoded payload. A `waiting_approval` contextual-inquiry Ticket cannot be processed by the current worker without a distinct, explicit transition into a review-only queue state.
- `TaskQueue.approve()` is the existing generic human approval transition. It changes `waiting_approval` to `queued` and sets `_approved`; contextual-inquiry approval now requires the validated attachment flags plus a durable trusted attachment event. The public `record_event()` API rejects that reserved event type, so setting payload flags alone cannot bypass the gate. Reusing generic approval to authorize pre-approval review would still collapse two different decisions: permission to inspect/analyze a case and approval of downstream work.
- worker.run_once() remains on the generic queued-task claim and generic TaskQueue.finish() path. It passes WorkerExecutionContext only to explicit opt-in handlers; the new run_contextual_inquiry_review_once() is a separate explicit entry point. AutonomousSupervisor can invoke that entry point only when a trusted contextual_review_handler is explicitly injected and a matching review_only authorization audit exists.
- `TaskQueue.record_workflow_event()` supports workflow-revision CAS and, for selected workflow events, verifies the current unexpired worker lease. It appends an event only; it does not atomically update the task payload. It is not by itself a context-attachment API.
- `TaskQueue.finish()` checks `status='running'` and optionally the lease owner, then stores every non-null handler result in the ordinary SQLite `payload_json` as `_result`. It does not enforce lease expiry. Consequently, a review handler must never return plaintext case fields, source excerpts, stakeholder statements, or unredacted model output. Any durable result must be explicitly sanitized or separately DPAPI-protected, and its attachment/event must be atomic and lease-fenced.
- Worker progress telemetry currently uses generic summaries rather than task payload text. That invariant must remain true for the contextual-review path, including exceptions and failure guidance.
- `AutonomousSupervisor._next_local_workflow_id()` still selects only `local_workflow`, `video_pipeline`, and `review_followup_research`; contextual inquiry is not added to that offline allowlist. A separate optional Commander hook selects only a `waiting_approval` contextual inquiry with a matching `review_only` audit, and only when a trusted handler is injected. `DEFAULT_HANDLERS` remains unchanged.

### Required two-decision model

1. Keep the existing initial Ticket in `waiting_approval`. Case-storage consent permits ciphertext retention only; it does not authorize review execution.
2. A narrowly named, audited review_only human decision is recorded by authorize_contextual_inquiry_review_only() with a task-version CAS. It does not queue or dispatch the Ticket, set _approved, or mark context attached.
3. AutonomousSupervisor has an optional Commander-owned dispatch hook. It remains inert by default; the CLI constructs a local handler only with `--enable-contextual-review`, an explicit local provider, a loaded model, and a loopback URL. It selects only a matching review_only-authorized Ticket. No cloud provider or cloud fallback is accepted.
4. The TaskQueue lease-fenced encrypted result-completion transaction, WorkerExecutionContext submission method, and dedicated review-only runner are implemented. Generic payload mutation or generic finish() remains forbidden for sensitive review output.
5. After the review result is available, require a **separate downstream human decision** before any knowledge persistence, claim adjudication, or action experiment. Preserve `ContextualInquiry.consent_to_store` as a distinct long-term-memory consent; the DPAPI case-storage consent must never imply it.
6. Continue negative tests for forged/missing authorization and claim audits, duplicate/replayed completion, lease expiry during decrypt/validation, malformed envelope schemas, plaintext leakage in logs/telemetry, generic worker dispatch, and attempts to use review-only authorization as downstream approval.

The lease-fenced encrypted result attachment transaction, WorkerExecutionContext submission method, dedicated review-only runner, optional Commander-owned dispatch hook, and local-only review handler are implemented. The hook is disabled unless an application explicitly injects a trusted handler; the CLI does so only with the explicit local-review flag and a verified loopback model configuration. It selects only a Ticket with a matching review_only audit and does not use generic claim_next() or finish(). Review-only authorization still does not approve downstream actions. No live model call or real case review has been run; default runtime remains inert for contextual inquiry. Private Python methods are not an isolation boundary against arbitrary same-user code.

## Encrypted review-result completion transaction — 2026-11-21

- TaskQueue.complete_contextual_inquiry_review_only() is the dedicated queue-side completion boundary. Under BEGIN IMMEDIATE, it checks the exact running Ticket, updated_at CAS, Worker lease owner and expiry, the separate human review-only authorization audit, and the matching dedicated claim audit.
- It decrypts and revalidates the stored inquiry, decrypts the submitted DPAPI result envelope, and validates a canonical version-1 review-result schema bound to the inquiry ID. Findings can be only support_candidate, counter_candidate, or unresolved; they cannot assert verified/support/refute verdicts. Observation and hypothesis references must resolve to IDs in the encrypted inquiry.
- Immediately before the state transition it rechecks lease expiry. The same transaction stores only review_result_envelope ciphertext, updates the validated-attachment flags, emits the fixed non-sensitive attachment audit event, returns the Ticket to waiting_approval, and clears the lease. It never writes review plaintext to _result or event payloads and never sets _approved.
- Focused psmux regressions: 166 tests passed, 0 failures across TaskQueue (46), Worker (36), contextual-inquiry security (8), bridge (18), CLI (5), AutonomousRuntime (27), local review handler (10), model client (6), and model-call context (10). After the loopback redirect guard was added, all 7 tests in `test_conversations_and_model_client.py` passed.
- `LocalContextualInquiryReviewHandler` is explicitly opt-in. It accepts only normal-safety inquiries, uses a strict JSON schema with support/counter candidates or unresolved findings, verifies all references against the case, checks the live lease before/after model inference and before encryption, and stores only a DPAPI envelope. The model endpoint must be credential-free HTTP loopback `/v1`; `LMStudioClient` disables proxy use and rejects HTTP redirects in this mode, preventing prompt forwarding to a redirect target. No model or real-case data was invoked during tests.

## Human review-result reader — 2026-11-21

- `TaskQueue.load_contextual_inquiry_review_result()` is a read-only, non-generic reader. It requires a `waiting_approval` Ticket, validated attachment flags, exactly one matching review-only authorization event, Worker claim audit and attachment event, a matching inquiry/Ticket idempotency key, and valid DPAPI case/result envelopes.
- It decrypts only into memory and returns the validated review-result object. It does not return the original case, modify the Ticket, append events, approve work, write `_result`, or persist plaintext.
- No terminal reveal command is provided: psmux persists stdout in job logs, which would reintroduce plaintext-at-rest leakage. The authenticated read-only panel is wired into the existing Tauri/Svelte dashboard: the list endpoint returns task IDs/timestamps only, and the detail endpoint calls the audited TaskQueue reader under the existing loopback/Bearer/Origin boundary with Cache-Control: no-store. The UI decrypts only on explicit click, renders in memory, clears the result on close/navigation, and has no approval or knowledge-persistence action. Status API tests (42) and frontend tests (55) passed; Svelte check reported 0 errors/0 warnings and production build passed. Tauri desktop acceptance remains pending.
